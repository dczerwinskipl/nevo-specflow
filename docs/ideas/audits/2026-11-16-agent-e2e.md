### Gaps for "Ask agent" (stage 2)

1. **Creating Tasks.** I had to enter the 6 Tasks (id, type, title, summary) in the UI and run 6 `tasks edit` commands for dependencies and context. Under the hood, an agent mode needs an Engine write path that works during a turn, such as a delegated claim or a Runtime API with the Session identity.
2. **New task dialog.** It has no dependencies, context or body. The body had to come from the agent editing `task.md` files.
3. **Finishing steps.** Every Finish (result, feedback, artifacts) and every Start was done by hand. The agent could fill the finish input itself, including "the finish input lists every draft Task".
4. **Approvals.** Review the breakdown and the Task Review were approved by me as owner. A reviewer-archetype agent step would need its own Session.
5. **Briefs.** I wrote every step brief by hand: step text, issue, paths and rules. The step's purpose and archetype, the Spec documents and the issue link should be injected automatically.
6. **Permissions.** About 30 Bash permission prompts came up in Accept edits mode, all read-only (`grep`/`sed`/`ls`), plus the CLI calls. Every one needed a click.
7. **Registration and commits.** New documents and the Specification documents written in each step have to be registered and committed by hand.
8. **Worktree setup.** The agent had to run `pnpm install` and the turbo build in the fresh worktree.

### Verdict

**Partly.** The Session agent wrote all of the Specification content end to end, and it was of high quality:

- overview, behaviour, ux, backend and decisions;
- 6 well-scoped Tasks with full bodies;
- one real, tested code change.

The product could not let it finish the job unaided. Task creation failed during the agent's own turn (D11, B1); two turns were lost (B2); and nothing the agent wrote was committed (B3, B4). Every workflow transition, approval and Task registration needed the owner.
