# Workflow and Task workbench decisions (November 2026)

This record keeps what the November 2026 UX round on the workflow and Task workbench decided
(owner review 2026-11-16, coordinator decisions 2026-11-17, owner decisions 2026-11-17 and
2026-11-18). The audit, the mocks and the working contracts are not kept. The rules live in the
documents named below; where this record and one of them disagree, the owning document wins and
this record is corrected.

## Decisions

| Topic                   | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                | Owned by                                                                                                                                                                                                                                                                                                          |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Status presentation     | One model for every Task surface: a status is a mark (registry glyph or `StatusIndicator` dot) and a label, chosen by the presented status id, never by the surface. Tones keep one meaning each (info running, success finished, attention a person must act now, danger failed or broken). On hold gets `circle-pause` and is neutral. There is no Blocked glyph until a Blocked state is designed.                                                                                                                                                   | [Task status presentation](specification-overview.md#task-status-presentation), [Status glyphs](../../../design-system/implementation/react/component-guidelines.md#status-glyphs), [Status and attention on a row](../../../design-system/principles/information-row-hierarchy.md#status-and-attention-on-a-row) |
| One name per state      | A status label matches its default group's name: **Ready to start**, **Cannot start** (`blocked`), **Done** (`completed`).                                                                                                                                                                                                                                                                                                                                                                                                                              | [Task status presentation](specification-overview.md#task-status-presentation)                                                                                                                                                                                                                                    |
| Requires attention      | It means the user must act. It is an overlay on a row, never a status, and the Engine reports it; the UI never derives it. A Task on hold is attention only while the user has to resume or cancel it (escalated with no step deciding it, waited on directly by an open Task, or keeping the step from finishing); its action is **Resume**, with **Cancel task** as the alternative.                                                                                                                                                                  | [Workflow kernel, Held Tasks](../../../architecture/workflow/workflow-kernel.md#continuation-and-attention), [ADR 0023](../../../architecture/decisions/0023-neutral-workflow-coordinator-and-manual-execution.md) item 9 (amended), [Requires attention](specification-overview.md#sections-and-order)           |
| Now block               | The step track is the position in the workflow definition, not progress (`Progress` position mode). The attempt number shows only from the second attempt on. There is one main action and at most one contextual secondary; Now never offers "View N tasks". The step id and revision appear only in the `⋯` note. An abandoned run shows no track while the outline does not say where it stopped. A step without document gates has no "Done when".                                                                                                  | [Now](specification-overview.md#sections-and-order), [Now block](workflow-execution.md#now-block), [Progress position mode](../../../design-system/implementation/react/component-guidelines.md#progress-position-mode)                                                                                           |
| Narrow Now              | Below a 40rem page content container Now is a flush band across the body padding (`AccentBlock bleed="narrow"`, a container query), not a card inside the sheet. From 40rem it stays the card.                                                                                                                                                                                                                                                                                                                                                          | [Now](specification-overview.md#sections-and-order), [Accent block bleed](../../../design-system/implementation/react/component-guidelines.md#accent-block-bleed)                                                                                                                                                 |
| Overview Tasks          | Always Task rows, with no mode switch by Task count: at most two per `row` group, chosen by the Runtime in one importance order shared with the Tasks page. "N more in <group>" opens the Tasks page filtered to that group (`?group=`), which never combines with `?blocking=specification`.                                                                                                                                                                                                                                                           | [Tasks](specification-overview.md#sections-and-order), [Task reads, Tasks page](../../../reference/api/task-reads.md#tasks-page), [Interaction model](interaction-model.md#reachability)                                                                                                                          |
| Tasks page              | It uses the Specifications list pattern: one shared `CollectionColumns` owner with a `task` preset (Task, Status), and the same Task row as the Overview.                                                                                                                                                                                                                                                                                                                                                                                               | [Tasks page](specification-overview.md#tasks-page), [Specifications list](specs-overview.md)                                                                                                                                                                                                                      |
| Full Task sections      | Below Wide a section starts open when it is small or holds a blocker, else collapsed with a summary. Context shows a short source label (**Default context** / **Own context list**) with its explanation in an info popover; the first change of a default has no confirm and is announced where it happens (a note in the row menu and in the Add dialog). **Use default context** compares with the Engine's `defaultEntries` and its confirm names what is lost.                                                                                    | [Full Task](workflow-execution.md#full-task-specsspecidtaskstaskid)                                                                                                                                                                                                                                               |
| Document content state  | There are three separate ideas: a template (a source of initial content), a generated baseline (for example `task.md` from the title and summary) and authored content. One model for Specification and Task documents: `contentState` is `baseline` while the file still has the recorded `baselineRevision`, else `authored`. Only a real edit ends it, never a metadata sync. The label is **Initial content only**. It is a separate fact from the workflow relation, and the two are named together only when both apply. "Template only" is gone. | [Registry rules](../../../architecture/runtime/specification-documents.md#manifest-schema-specificationyaml), [Document state label](documents-archetypes-ui.md#document-state-label)                                                                                                                             |
| Workflow document gates | Shipped workflow definitions are not changed to demonstrate the UI. Surfaces never show an empty "Done when" or requirements the workflow does not declare.                                                                                                                                                                                                                                                                                                                                                                                             | [Now block](workflow-execution.md#now-block)                                                                                                                                                                                                                                                                      |
| Close dialog            | It shows one outcome at a time, and never "Ready to close" while a check is pending, failed or blocking. Repository blockers are shown before confirming. No integration branch is assumed (`main` included): candidates are shown with their facts, nothing is preselected, and **Copy setting** becomes available only after a choice. Discarding is warned against, never offered. The dialog does not write project configuration.                                                                                                                  | [Close](workflow-execution.md#close), [Specification operations, Close](../../../reference/api/specflow-specification-operations.md#close)                                                                                                                                                                        |
| Close with Git off      | With `git.enabled: false` or no `git:` block, a Specification Close only archives in place: no commit, no integration and no repository precondition. The Ready facts say "Archives without Git (Git is off for this project)".                                                                                                                                                                                                                                                                                                                         | [Close with Git off](../../../architecture/runtime/specification-lifecycle.md#close-with-git-off-owner-decision-2026-11-17), [Specification operations, Close](../../../reference/api/specflow-specification-operations.md#close), [CLI](../../../reference/cli/specflow-specification-commands.md)               |
| Demo Runtime            | The demo runs the Engine's workflow in memory and serves the project routes, so the UI has no demo branch for Now, the Tasks page and the Full Task. The snapshot-based Task screen and the Task preview are removed.                                                                                                                                                                                                                                                                                                                                   | [ADR 0025](../../../architecture/decisions/0025-demo-runs-the-engine-in-memory.md)                                                                                                                                                                                                                                |

## Why no further ADR

Only two of these decisions change a durable, cross-cutting rule: the held-Task attention, which
amends [ADR 0023](../../../architecture/decisions/0023-neutral-workflow-coordinator-and-manual-execution.md),
and the demo Engine, which is [ADR 0025](../../../architecture/decisions/0025-demo-runs-the-engine-in-memory.md).
The status model is a product and design-system rule. The content state model and Close with Git
off are contained in the registry and lifecycle rules of their architecture documents, and they
supersede no ADR statement.
