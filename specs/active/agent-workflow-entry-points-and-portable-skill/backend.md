# Backend

## Contracts

**C1. Owner decisions in the step context (Engine).** `TransitionDescription` gains
`ownerDecision?: { reasons: ('confirmation' | 'effect')[]; effects?: string[] }`, computed by D17's
authority classification (`confirmation: owner`, owner-authority effects such as `approve-draft-tasks`).
`StepContext.finish` states that non-empty `taskDecisions` are an owner decision. `workflow context`
prints every result: id, label, target, the feedback rule, and "owner decision (<reasons>)". The JSON
carries the same data. This is information for the skill. Enforcement stays D17's.

**C2. Skill source and wrappers (CLI package, Engine commit).** One provider-neutral Markdown source,
`packages/specflow/skill/nevo-specflow.md`, copied to `dist/skill/` by the bundle, as the default
definitions are (architecture.md S1). The CLI renders and classifies the wrappers. The Engine's
`installProjectFiles` writes and commits them (S3), because only the Engine commits (ADR 0013). A wrapper is
YAML front matter (`name: nevo-specflow`, a one-line `description`), then the marker
`<!-- GENERATED by nevo-specflow <cli-version>; sha256 <body-digest>. Update with "nevo-specflow skill install". -->`,
then the body. `install` classifies each wrapper:

- missing: `written`;
- no marker: `kept` (not generated);
- the body's digest differs from the marker's: `kept` (edited);
- the marker's version is newer than this CLI: `kept` (newer);
- the body equals the shipped body: `unchanged`;
- otherwise: `updated`.

`--force` turns any `kept` into a write. `--dry-run` prints the plan.

**C3. Skill commands.** `skill show` and `skill install`, as skill.md (Commands) states. In the agent
command table, `skill show` is a `read` with no brief form (it stays out of briefs), and `skill install`
is `refused`. The table test keeps every command in exactly one placement. `init` writes the wrappers
after the definitions and commits both in one Engine commit (kind `project-init`, S4). Its result lists
the wrapper paths beside the definitions.

**C4. Ad-hoc brief (Runtime).** `renderAdHocBrief({ specification, scope, documents, documentTypes,
docsSearch? })` sits in `features/agent-execution/brief/`. It reuses `untrusted`, `oneLine`,
`BRIEF_TEXT_BUDGET` and `LINE_BUDGET`, and renders the operations from `AGENT_COMMANDS` filtered by the
ad-hoc scope (`renderOperations`). Its sections: the subject, the documents (at most 50, then "and N
more: run specs documents list"), the types, the operations, and the rules. The rules add: "This
conversation is not a workflow attempt. You cannot start or finish a step or draft Tasks. If asked to,
say that the owner uses Run with agent on the Specification." The whole brief is at most 16 KiB.
Documents and types come from an Engine read of the home Specification
(`readAgentSessionContext(specId)`), in the shape of `AgentStepContext`'s documents and types.

**C5. Ad-hoc brief delivery (Runtime, Sessions).** When an ad-hoc write Turn's capability is minted
(`scopeOf`, ad-hoc branch), the Runtime renders the brief, and the driver input becomes the brief, a
line `## Message from the owner`, then the owner's message unchanged. The `request` entry keeps the
owner's text. The brief is stored with the dispatch intent, in the same transaction, as a new
conversation entry of kind `brief` (a `TextPreview`, paged like any entry), and the stored Turn gains
`brief: { sha256, entryId }` (architecture.md S5, S6). `TurnSummary` does not change. The transcript
renders the entry as the SpecFlow brief part (ux.md). Read-only and attempt Turns carry none.

**C6. Create with an agent (UI over existing routes).** `POST /api/specs` and its operation are
unchanged (D5). The workflow comes from the archetype, so each archetype of the archetype catalogue
(`GET /api/specs/archetypes`, `ArchetypeInfo`) gains `firstStep: { id, title, agent: boolean }` of its
bound workflow (absent without one). The route's ETag covers it (D8, architecture.md S7).
`create-options` does not change. After the Create operation is `completed`, the UI sends
`POST .../workflow/agent-execution` with `expected: { step: firstStep.id }`, the chosen `provider`,
`model` and `effort`, and a `requestId` that is a UUID v5 of `<createOperationId>:agent-start` (S8).
That way a repeat of the same Create replays the same start.

## Data and ownership

- Engine: owner-decision classification, the ad-hoc context read, `firstStep` in the catalogue, and
  the project-file install with its commit kinds (`skill-install`, `project-init`) and its ledger owner
  (`skill`). Nothing else new is persisted.
- CLI package: the skill source, the wrapper rendering and classification, and the commands. The
  wrappers are project files, committed by the Engine.
- Runtime: the ad-hoc brief, its `brief` entry and the Turn's `brief` fact (Session storage, like the
  message).
- UI: the Create chaining and the transcript part.

## Invariants

- No new transition, actor, claim, broker operation or scope. An ad-hoc scope stays D11b's.
- `skill install` writes only the two `SKILL.md` paths, and never another folder or file.
- The brief never contains the capability, a credential or an absolute path.
- A Create with an agent never sends a second start under a new request id.

## Errors and recovery

- `skill install`: `BRANCH_PROTECTED` and `COMMIT_BLOCKED` as `definitions install`. A link or special
  file refuses before writing. `SPEC_BUSY` while an agent Turn holds the project. A wrapper that
  changed after it was classified refuses the whole install with `PROJECT_FILE_CHANGED`. An
  interrupted install's files are committed by the next install, and Close refuses while they are
  uncommitted.
- Ad-hoc brief: when the documents read fails, the brief is still sent without the document list and
  says so. An ad-hoc write Turn is never dispatched without a brief.
- Create chaining: a refused or lost start is `WORKFLOW_AGENT_UNAVAILABLE`, or unknown. The UI lands
  on the Overview (ux.md). The same request id replays. A different payload is
  `WORKFLOW_STATE_CONFLICT`, as E6 defines.

## Verification

- Engine: `describeTransitions` marks the `approved` breakdown-review result (effect) and a
  `confirmation: owner` result. `workflow context` prints them. `installProjectFiles`: path allowlist,
  link refusal, `PROJECT_FILE_CHANGED`, `SPEC_BUSY`, ledger owner `skill` and the Close hold.
  `firstStep` for an agent first step, a human first step and no binding.
- CLI: install classification table (C2), `--force`, `--dry-run`, a link refusal, a protected branch,
  init with and without `--no-skill` (one `project-init` commit), the command-table placement test,
  and `skill show` without a project. The bundle fails without the skill source.
- Runtime: the ad-hoc brief snapshot, the budgets and the 50-document cut, delivery order, the
  `brief` entry written with the dispatch intent (none for an undispatched Turn), redaction, no brief
  on read-only or attempt Turns, and the catalogue ETag changing with `firstStep`.
- UI: the Create stories (agent first step, none, refused start, lost answer) and the transcript part.
- Acceptance A1 to A11 (behaviour.md), A1 to A3 with a packaged CLI and Runtime stopped.
